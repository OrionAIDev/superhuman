# Phase 3.3: Preflight review (pre-acceptance fan-out)

A dedicated adversarial fan-out that runs **after** Phase 3.2 (docs sync) and **before** Phase 4
(acceptance). Phase 3.1 reviews each chunk as it lands; this phase gives the PM three *independent*
skeptical reports on the **whole delivered chunk set** before sign-off — correctness, security, and
design-conformance — in parallel, without more wall-clock. It is a **review step, not a gate**: it
produces a GO/NO-GO the PM reconciles into the acceptance packet handed to Phase 4.

## Inputs

- The delivered chunk set (final commits) and its diff since the last approved baseline.
- `REQUIREMENTS.md`, `DESIGN.md`, `PLAN.md`, and the Phase 3.1 review history.
- `references/definition-of-done.md` (the standing bar the delivery must clear).

## Steps

1. **Single-turn parallel fan-out.** The PM issues **three `<dispatch:agent>` calls in ONE
   assistant turn** so they run concurrently. All three lenses are **read-only** on the delivered
   code, so they are parallel-safe by default (per `references/orchestration-patterns.md` Pattern 3
   and the `roles/pm.md` parallel checklist).

   - **Lens 1 — Correctness / architecture.** Dispatch with the `references/roasting-code/` brief
     against the delivered chunks: walk the attack surfaces (auth, data integrity, races, rollback,
     error handling, boundary state, schema/contract compatibility, observability). "Prove this
     shouldn't ship as-is."
   - **Lens 2 — Security (inline lens; see checklist below).** Dispatch a fresh reviewer with the
     security checklist in this file, using the `references/roasting-shared/roast-framework.md`
     severity model + Categorize-findings prefixes. This lens is new — Phase 3.1's reviewers don't
     cover it.
   - **Lens 3 — Design conformance.** Dispatch with the `references/roasting-design-specs/` brief,
     re-run against the **delivered** chunks: does the built thing still satisfy the approved
     DESIGN.md, or did implementation drift from it?

2. **Single-assistant-turn rule (mandatory).** Issue all three dispatches in one turn — sequential
   turns serialize execution and defeat the pattern. This mirrors the PM's own parallel-dispatch
   discipline (the high-stakes-parallelism gate) and the `/ship`-style fan-out. The three reviewers
   are flat: none delegates to another (role-dispatches-role is forbidden).

3. **Merge in the PM thread.** Once all three reports return, the PM (not a sub-reviewer)
   synthesizes them, de-duplicates overlapping findings, and applies the roast-framework severity
   prefixes — **lead with what matters** (correctness + security first, cosmetics last). Emit a
   single block:

   ```markdown
   ## Preflight decision: GO | NO-GO

   ### Blockers (must fix before acceptance)
   - [lens: Critical/required finding + file:line]

   ### Recommended fixes (should fix)
   - [lens: Optional finding + file:line]

   ### Acknowledged risks (accepting anyway)
   - [risk + mitigation]

   ### Rollback plan
   - Trigger conditions: [what would prompt a rollback]
   - Rollback procedure: [exact steps — branch/tag/archive]
   - Recovery objective: [target]

   ### Full lens reports
   - [correctness/architecture] · [security] · [design-conformance]
   ```

   The **rollback plan is mandatory before any GO**. Any **Critical/Blocker** finding defaults the
   verdict to **NO-GO** unless the user explicitly accepts the risk at acceptance.

4. **Reconcile into acceptance.** The PM appends the decision block to `SUPERHUMAN.md` and carries
   it into the Phase 4 acceptance packet. On **NO-GO** or any Blocker: do **not** proceed to
   acceptance — fix and re-run the relevant lens. If a finding reveals a design or requirements
   problem (not just a code fix), that is a moderate+ drift event → **G6**, not a silent patch.

## Security lens (inline spec)

The Lens-2 reviewer walks this checklist and reports issues-only, prefixed by severity. If the
profile declares a `review_checklist` overlay, the reviewer walks that **in addition** — a project
may add organisation-specific checks, never remove the baseline ones:

- **Secrets and sensitive data:** no secrets, credentials, tokens, or regulated personal data in
  code, logs, or version control; sensitive records touched only through their supported access
  path, never improvised file writes.
- **Untrusted input:** data from external sources (APIs, user content, config, LLM output) is
  validated at the boundary before use in logic, a query, or a shell command; no injection
  (shell/SQL/prompt) surface left open.
- **Auth / authz:** any new surface checks authentication and authorization where required; exit
  codes / error paths don't leak privileged state.
- **Dependencies:** new dependencies are from trusted sources (preferred-libraries first), pinned,
  with no obviously vulnerable version.
- **Release safety:** nothing in the delivery silently targets a rung whose `promote_into` policy
  names an approver, without that approver having signed off; an unattended run has not stood in
  for an approval the profile requires.

## Outputs

- The Preflight decision block (GO/NO-GO + Blockers + fixes + risks + rollback) in `SUPERHUMAN.md`,
  carried into the acceptance packet.

## Exit criteria

- A GO decision (or a NO-GO fully resolved and re-run), reconciled into the Phase 4 acceptance
  packet. Any Blocker is closed or explicitly risk-accepted by the user at acceptance.
