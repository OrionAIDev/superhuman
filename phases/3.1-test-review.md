# Phase 3.1: Test & review (per chunk)

## Inputs

- Developer's chunk output (commits)
- PLAN.md chunk acceptance criteria
- TEST.md test cases relevant to this chunk

## Steps (per chunk, after Developer reports DONE)

1. **Parallel dispatch** (per DESIGN.md §8 — reviewers + tester are read-only on code, so parallel by default):
   - **Tester (mode: spec-compliance)** — verifies the chunk's output matches PLAN.md acceptance criteria + REQUIREMENTS items.
   - **Tester (mode: test execution)** — runs the tests relevant to this chunk.
   - **Code-quality reviewer** (separate `<dispatch:agent>` with reviewer prompt from references/requesting-code-review/code-reviewer.md) — reviews diff for quality issues.
   - **Single-assistant-turn rule (mandatory).** Issue all three dispatches in ONE turn —
     sequential turns serialize execution and defeat the pattern, so a "parallel" step that is
     actually serial costs the wall-clock it was meant to save. Same discipline as
     `phases/3.3-preflight-review.md` step 2, stated here because this phase runs far more often.
     The three are flat: none delegates to another (role-dispatches-role is forbidden).

2. **Wait for all three** (consolidate into one G5 report regardless of cadence).

3. **QA coverage check** (sequential, after the above three).
   - QA reviews tests for gaps vs TEST.md targets.
   - QA fails the review if convention-required docs are missing (e.g., Python docstrings).
   - QA applies the **standing Definition of Done** (`references/definition-of-done.md`) as the
     per-chunk floor for G5: the chunk's Correctness and Quality sections must be satisfied, not
     just its acceptance criteria. A chunk that meets its acceptance criteria but fails a DoD item
     (no runtime verification, a regression, a missing docstring, a bypassed sensitive-data guard)
     is `issues_found`, not approved.

4. **Drift classification.** PM collects triggers, classifies per §11.2, decides G5 fold / G6 escalation.

5. **G5: Per-chunk results.**
   - **If cadence = per-chunk:** Type A — full summary + delta-report + continue/revisit options. **PAUSE for user input** before any subsequent dispatch.
   - **If cadence = on-divergence:** Type B — one-liner ("Chunk N/M complete: ✓ spec, ✓ quality, K/K tests pass; continuing."). **DO NOT PAUSE.** Per SKILL.md "Autonomous phase progression" rule: immediately continue — if more chunks remain in PLAN.md, dispatch the next Developer; if all chunks complete, proceed to Phase 3.2. Do not wait for the user to type "continue" or "status?" — that pattern erodes trust that the orchestrator is actually driving.
   - **If moderate+ drift detected:** G6 (interrupts G5; uses delta-report template). **PAUSE for user input.**

6. **Retuning** (after G5 if Type A, or after G6 resolution): append entry per §7 rule 9.

## Outputs

- Test results (per chunk)
- Spec-compliance verdict (per chunk)
- Code-quality review (per chunk)
- QA coverage report (per chunk)
- Updated SUPERHUMAN.md chunk log, drift notes, retuning notes

## Exit criteria

- All reviews verdict = approved.
- Drift classification ≠ critical (else loop back per §11.3 actions).

7. **Worktree cleanup.** After test/review: run `git worktree prune` to clean stale per-chunk worktree registrations.

Next: loop to Phase 3 for next chunk; when all chunks complete → Phase 3.2.
